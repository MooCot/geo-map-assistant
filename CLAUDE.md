# CLAUDE.md

Bootstrap-контекст для проєкту `geo-map-assistant` (portfolio/demo WordPress-плагін).

## Мета

Demo-плагін, що демонструє ті самі навички, що й `ai-content-assistant`: кастомна адмінка, фонова черга через WP-Cron, самостійна архітектура плагіна, інтеграція зовнішнього API — але з картографічним доменом (Leaflet).

Аудиторія: README на GitHub зі скріншотами та GIF; технічно зацікавлені можуть підняти локально одним `docker compose up -d --build`.

## Зафіксовані рішення (до коду)

- **Джерело адреси:** окреме поле (post meta `gma_address`), редагується в мета-боксі поста.
- **Геокодер:** Nominatim (OpenStreetMap). Політика сервісу: не більше 1 запиту на секунду, обов'язковий ідентифікуючий `User-Agent`.
- **Mock-режим за замовчуванням:** `MockGeocoder` повертає детерміновані координати без мережі (демо працює одразу після `docker compose up`). Nominatim — якщо в налаштуваннях увімкнено.
- **Карта:** Leaflet 1.9.4, vendored у `assets/` (без build-степу; карта працює без сторонніх CDN). Тайли OSM з обов'язковою атрибуцією.
- **Порт демо:** `8081` (щоб не конфліктувати з `ai-content-assistant` на `8080`).
- **Стек:** PHP 8.2+, WordPress 6.6 (образ `wordpress:6.6-php8.2-apache`), MySQL 8.0, Guzzle для HTTP.

## Обсяг — 2 фічі + налаштування

1. **Адмін-дашборд** — статкарточки (pending/processing/done/not_found/error), таблиця задач геокодингу з polling, ручний retry для `error`.
2. **Карта** — shortcode `[gma_map]`, маркери готових точок, попап із посиланням на пост (спільний `modal.js`-патерн).

Налаштування: тайл-провайдер, центр і зум за замовчуванням, вибір геокодера (mock / nominatim).

## Структура

```
geo-map-assistant.php          # plugin header + bootstrap (composition root)
composer.json                  # guzzlehttp/guzzle + пін тест-стеку
includes/                      # PSR-4 "GMA\\" → includes/
assets/                        # leaflet vendored + власні JS/CSS
docker/init-test-db.sql        # wordpress_test для integration-тестів
docker-compose.yml             # wordpress + db + wp-cron (сайдкар) + wp-cli (install + activate)
tests/Unit/                    # чистий PHPUnit, без WP
tests/Integration/             # WP_UnitTestCase у контейнері
```

## Тести

- **Unit** (`composer test:unit`) — без WordPress, запускається будь-де.
- **Integration** (`docker compose exec wordpress php vendor/bin/phpunit -c phpunit.integration.xml`) — реальний WP + реальна БД.

## Версійні прив'язки (перенесено з `ai-content-assistant`, перевірено практикою)

- `wp-phpunit` тієї самої мінорної версії, що й образ WordPress (`6.6.*`).
- `phpunit ^9.6` (wp-phpunit 6.6 викликає API PHPUnit 9, видалений у 10).
- `doctrine/instantiator` пін на `2.0.0` (2.1+ несумісний з PHP 8.2).
- `WP_AUTO_UPDATE_CORE=false` разом з реальним WP-Cron (інакше ядро саме оновлюється).
- Очікування MySQL у wp-cli — через сирий `mysqli`, не через `wp` чи `mysqladmin`.

## Надійність черги — проаналізовано для геокодингу

Попередні правила з `ai-content-assistant` перенесені як гіпотези і перевірені тут на новому домені. Нижче — що змінилось.

### 1. Класифікація помилок

| Ситуація | Клас | Дія |
|---|---|---|
| Nominatim повернув `200` з порожнім масивом | `not_found` (термінальний) | Без автоповтору: адреса не знайдена — повтор не змінить відповідь. Ручний retry дозволений |
| `400`, некоректна адреса | `error` (термінальний) | Без автоповтору |
| `429` | Тимчасова | Ретрай з backoff; якщо є `Retry-After` — не раніше за нього |
| `5xx`, таймаут, мережева помилка | Тимчасова | Ретрай з backoff |
| `403` або інший системний збій (зокрема відсутній/відхилений `User-Agent`) | Системна | Не спалює спроби жодної задачі: брейкер відкривається, задачі лишаються `pending` без зміни `attempts` |

Попередня модель «будь-яка помилка = ретрай» тут невірна: вона витрачала б спроби на адреси, яких не існує.

### 2. Атомарність і протухлі claim (lease)

Проблема: процес падає між claim і `markDone` — задача назавжди в `processing`. Попередня модель цього не покривала.

Рішення:
- Таблиця `wp_gma_geo_jobs` має колонки `claim_token` (VARCHAR, випадковий на кожен claim), `locked_until` (DATETIME, lease 5 хв) і `attempts`.
- Claim — одна умовна `UPDATE`: `status='pending' AND next_retry_at <= NOW()` **або** `status='processing' AND locked_until < NOW()` (протухлий claim). Одночасно ставимо новий `claim_token`, `locked_until` і **збільшуємо `attempts`**. Лічильник іде на початку спроби, а не в момент провалу: так задача, що падає на кожному запуску (наприклад, процес завершується через фатальну помилку), рано чи пізно вичерпає спроби і не зациклиться.
- Завершення (`markDone` / `markError` / `markNotFound`) — `UPDATE ... WHERE id=? AND claim_token=?`. Fencing-токен: якщо lease вичерпався і задачу забрав інший worker, старий не перезапише його результат. Перевіряємо `affected_rows`; `0` означає «результат відкинуто».

### 3. Ретраї

- `MAX_ATTEMPTS = 3` (разом з першою спробою). Затримка перед повтором: 1 / 2 / 4 хв через `next_retry_at`, як і раніше.
- Після вичерпання спроб тимчасової помилки статус стає `error`.
- Ручний retry для `error` і `not_found`: `UPDATE ... WHERE status IN ('error','not_found')`, скидає `attempts` і `next_retry_at`. Той самий compare-and-swap, подвійний клік не ставить задачу двічі.

### 4. Бюджет запитів під ліміт 1 req/s

- Крон-тік раз на 60с (сайдкар `wp-cron`). Батч = 10 задач, пауза ≥ 1.1 с між запитами, це ~11 с на тік з запасом.
- Ліміт іде через `GeocoderManager`, а не через батч: він зберігає час останнього запиту (`wp_options`, `autoload=false`) і спить до 1.1 с від попереднього. Так обмеження тримається і для ручного «Геокодувати всі» (AJAX-драйв), і для крону.
- Один запит = одна задача. Однакові адреси в різних постах у межах одного батчу не дублюємо: кеш результату за нормалізованою адресою (`address_hash`) — опціонально, якщо вистачить часу.

### 5. Ідемпотентність запису координат

- `address_hash` (SHA-256 нормалізованої адреси) зберігається в задачі. Збережений результат використовується повторно, поки хеш не змінився.
- Зміна адреси поста (хук `save_post`) робить `UPSERT` задачі: новий `address_hash` → `status='pending'`, `claim_token=NULL`. Якщо старий worker ще тримає задачу зі старим хешем, його `markDone` не спрацює (токен уже не збігається), і застарілий результат не потрапить у базу.
- `UNIQUE KEY (post_id)` — одна задача на пост; повторна реєстрація того самого адреса — no-op.

### Що ще треба перевірити live (не можна вирішити читанням)

- Реальну відповідь Nominatim на неіснуючу адресу (`200 []` чи щось інше) і на `429`.
- Чи Nominatim приймає наш `User-Agent` із контактом (політика вимагає ідентифікації).
- Чи укладається батч 10 задач у тік 60с з паузами 1.1 с на реальному мережевому шляху з контейнера.

## WP-Cron і стабільність у Docker — перенесено (зафіксовано)

- Вбудований pseudo-cron WordPress (loopback-запит на себе при кожному хіті) у локальному Docker ненадійний: лок `doing_cron` оновлюється, батч не запускається. Тому `DISABLE_WP_CRON=true` і окремий сайдкар `wp-cron`, який раз на хвилину викликає `wp-cron.php` (заміна системного crontab).
- `WP_AUTO_UPDATE_CORE=false` вмикаємо ОДНОЧАСНО з реальним WP-Cron. Інакше вперше запрацьований cron запускає автооновлення ядра, і інсталяція мовчки стрибає з пінованої версії. Знадобилось перестворити volume з файлами ядра (без БД).

## Автоустановка через `wp-cli` — перенесено (зафіксовано)

- Очікування MySQL — через сирий PHP `mysqli_connect()` з `mysqli_report(MYSQLI_REPORT_OFF)`, не через `wp` (кожен виклик `wp` — повний bootstrap WP, 60 викликів = хвилини) і не через `mysqladmin`/`wp db check` (MariaDB-клієнт в образі `wordpress:cli` падає на MySQL 8: TLS і `caching_sha2_password`).
- Кожен крок ідемпотентний: `wp core install ... || true`, потім `wp plugin activate`.
- Тестова БД `wordpress_test` створюється через `docker/init-test-db.sql` (`/docker-entrypoint-initdb.d/`), бо користувач `wordpress` не має прав `CREATE DATABASE`. Без цього integration-тести падають на чистому клоні з `db_select_fail`.

## Bootstrap інтеграційних тестів — перенесено (зафіксовано)

- `wp-phpunit` запускає `install.php` окремим процесом через `system()`, який перечитує конфіг за шляхом `WP_TESTS_CONFIG_FILE_PATH`. Константи БД і тестів мусять жити у файлі `tests/wp-tests-config.php`, а не в `define()` всередині bootstrap-скрипта. Інакше дочірній процес падає з `Undefined constant WP_TESTS_DOMAIN`.

## Перевірка живим прогоном — обов'язково

Кожна ключова поведінка перевіряється на живому Docker-стеку (`docker compose down -v`, `up -d --build`, реальні HTTP-запити), а не лише читанням коду. Чисті volumes — окремо, бо багато багів проявляються лише на першому старті.

## Що свідомо НЕ робимо

- Публічний живий хостинг демо.
- Реальні виклики Nominatim без явного увімкнення в налаштуваннях.
- Білд-степ (webpack/gulp), фреймворки JS.
